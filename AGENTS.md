# Project instructions

## Explanation and writing

Start with the answer. Avoid setup, praise and category labels. Avoid the “X, not Y” construction. State the point before describing it. Minimise adjectives. Do not make ordinary observations sound philosophical or symmetrical.

## Living design

Maintain `docs/DESIGN.md` as the explanation of the entire project. Update it whenever a meaningful piece of logic is created, decided, modified, renamed, deleted or restructured.

## Agent journal

Maintain `docs/_J-Agent-productivity-for-neurodivergents.md`. Record every activity and why it was performed. Use `## Date - Model - Workspace`, with the actual model family and client. New days go at the top. When another model or workspace already has entries for the day, add `### Model - Workspace` under that day.

## Code narration

Every code file touched needs a header comment explaining what the file does and where its contents are called or referenced. Explain meaningful code blocks with narrative comments. Markdown and text files are exempt.

## Agent skills

### Issue tracker

Track engineering work in local Markdown under `.scratch/`. Before publishing or claiming tickets, read `docs/agents/issue-tracker.md`.

### Triage labels

Use the five default triage roles. Before changing ticket status, read `docs/agents/triage-labels.md`.

### Domain docs

Use the single-context glossary and ADRs. Before implementation or review, read `docs/agents/domain.md`.
