# Reusable multimodal memory search

MiniSearch supplies BM25+ word ranking. It can search text extracted from a saved image, but it cannot infer what the pixels depict. On-device semantic image retrieval needs a paired image/text encoder plus a vector index. UForm supplies a first-party Swift/Core ML implementation worth probing; Apple Vision supplies OCR without bundling an OCR model.

Research checked 22 October 2026. This is source/licence evaluation, with no production implementation, no new product scope, and no device performance result. The separate [MiniSearch native probe](../verification/minisearch-native-probe-2026-10-22.md) establishes its own measured conditions. Those measurements do not establish OCR, image-encoder, query-model or keyboard-extension performance.

## MiniSearch: exact scoring and image boundary

MiniSearch 7.2.0 at `3d239d1c3ae7aef1bf5d8945dd7b5f0709f646f5` implements **BM25+** in `src/MiniSearch.ts`, through `calcBM25Score`. Defaults are `k = 1.2`, `b = 0.7`, `d = 0.5`. The added `d` term is the BM25+ lower-bound adjustment. Rarity, term frequency and field length contribute to lexical relevance; fuzzy/prefix matching and boosts provide additional behavior. Omnisearch pins MiniSearch 7.1.0, so the integration must record its actual version. [Scorer and defaults](https://github.com/lucaong/minisearch/blob/3d239d1c3ae7aef1bf5d8945dd7b5f0709f646f5/src/MiniSearch.ts#L2148-L2160), [Omnisearch dependency](https://github.com/scambier/obsidian-omnisearch/blob/0a4e93b2ed155b84c3fe89f6d2d19c5a8c171a87/package.json).

A screenshot whose extracted text says “application closes Friday” can be found through those words and linked back to the image. A photograph of a red chair with no accompanying words requires an image/text model to answer “red chair”. Merely placing a filename, binary image or vector in MiniSearch will not supply that understanding. These examples describe the architectural distinction, not measured retrieval quality. [MiniSearch text-engine contract](https://github.com/lucaong/minisearch/blob/3d239d1c3ae7aef1bf5d8945dd7b5f0709f646f5/README.md).

## Three evidence paths for one saved image

| Evidence | Reuse | What it can contribute | Limit |
| --- | --- | --- | --- |
| Caption/note, filename, saved source | MiniSearch or FTS5 | Remembered wording, URLs, names | Only text actually supplied/indexed |
| Recognized image text | Apple Vision `VNRecognizeTextRequest` | Screenshots, documents, receipts, photographed text | OCR can misread or miss text; language/revision support varies |
| Visual content embedding | Matched image/text encoder + USearch/sqlite-vec/exact vector retrieval | Natural-language descriptions of visual scenes and objects | Requires model assets, query encoding, relevance evaluation and device resources |

Apple states Vision text recognition runs on the device and offers accurate/fast paths, recognized strings, confidence and text bounding boxes. The supported-language query depends on recognition path and revision. Keep source image and OCR provenance separate, so errors can be corrected without altering the original. The Apple framework is a platform dependency rather than an independently redistributable open-source OCR engine. [Apple OCR guide](https://developer.apple.com/documentation/vision/recognizing-text-in-images), [OCR request](https://developer.apple.com/documentation/vision/vnrecognizetextrequest).

Vision feature prints support image-to-image distance. They do not expose a paired text encoder that makes an arbitrary sentence comparable in the same space. Use them for visual similarity or duplicate candidates if those behaviors are selected later; they do not by themselves fulfill text-to-image Find. [Feature-print request](https://developer.apple.com/documentation/vision/vngenerateimagefeatureprintrequest), [distance API](https://developer.apple.com/documentation/vision/vnfeatureprintobservation).

## Reusable paired encoder candidates

### UForm: first integration candidate

Upstream `unum-cloud/uform` at `f4beec53743b44ffaad4ff754d65f6c2d347bbd9` (30 October 2025, v3.1.4) has a first-party Swift package and Apache-2.0 licence. Its manifest declares iOS 16 and macOS 13; it pins a `swift-transformers` fork revision for tokenizer/Hub support. `swift/Encoders.swift` contains `TextEncoder`, `ImageEncoder`, local-path and model-download constructors, tokenizer/attention-mask construction, image resize/crop/normalization and Core ML loading. This replaces substantial inference plumbing. It is a candidate source dependency, without an app/extension build result yet. [Manifest](https://github.com/unum-cloud/uform/blob/f4beec53743b44ffaad4ff754d65f6c2d347bbd9/Package.swift), [Swift implementation](https://github.com/unum-cloud/uform/blob/f4beec53743b44ffaad4ff754d65f6c2d347bbd9/swift/Encoders.swift), [licence](https://github.com/unum-cloud/uform/blob/f4beec53743b44ffaad4ff754d65f6c2d347bbd9/LICENSE).

Publisher model `unum-cloud/uform3-image-text-english-small`, revision `a8d990ed0dc6340b9c25cb47f06f86b9ecb67fa6`, declares Apache-2.0 and provides paired encoders with 256-dimensional outputs. The text path accepts up to 64 tokens and the image path uses 224 × 224 inputs. Core ML packages include ordinary and neural-optimized variants. English support is the stated scope of this checkpoint; mixed-language visual search needs a separately selected/evaluated multilingual model. Publisher retrieval results are evidence of model capability on its datasets, without establishing our personal corpus or keyboard behavior. [Model card](https://huggingface.co/unum-cloud/uform3-image-text-english-small/blob/a8d990ed0dc6340b9c25cb47f06f86b9ecb67fa6/README.md), [configuration](https://huggingface.co/unum-cloud/uform3-image-text-english-small/blob/a8d990ed0dc6340b9c25cb47f06f86b9ecb67fa6/config.json).

Registry file metadata at that revision lists about **22.1 MB** for the neural image weight file and **38.0 MB** for the neural text weight file, before model graphs, tokenizer, compilation and runtime allocations. The ordinary weight files are about 87.1 MB and 151.5 MB. These are file-byte sizes, not RAM measurements. The query-side text model alone can be substantial for a keyboard. Prefer companion-provisioned pinned local assets; the convenience model-name constructor downloads from the Hub and must not become a keyboard cold-open dependency. [Exact model files](https://huggingface.co/unum-cloud/uform3-image-text-english-small/tree/a8d990ed0dc6340b9c25cb47f06f86b9ecb67fa6), [Swift guide](https://github.com/unum-cloud/uform/blob/f4beec53743b44ffaad4ff754d65f6c2d347bbd9/swift/README.md).

### MobileCLIP: useful Swift code, model distribution gate

Apple's `ml-mobileclip` at `48faa0fea4b08d74188b3841771aca6ff2c92852` (11 September 2026) includes an iOS 17.2 demo with separate Core ML image/text encoders. Reusable code candidates include `ios_app/MobileCLIPExplore/Models.swift`, `ZSImageClassification.swift`, `Extensions.swift` and `Tokenizer/CLIPTokenizer.swift`. The tokenizer uses 77 tokens; this is a token limit, not 77 characters. The demo shows actor-based inference, crop/resize and cosine scoring. It remains a scene-classification example rather than a production vault/index lifecycle. [Demo README](https://github.com/apple-aiml-research/ml-mobileclip/blob/48faa0fea4b08d74188b3841771aca6ff2c92852/ios_app/README.md), [models](https://github.com/apple-aiml-research/ml-mobileclip/blob/48faa0fea4b08d74188b3841771aca6ff2c92852/ios_app/MobileCLIPExplore/Models.swift), [pipeline](https://github.com/apple-aiml-research/ml-mobileclip/blob/48faa0fea4b08d74188b3841771aca6ff2c92852/ios_app/MobileCLIPExplore/ZSImageClassification.swift), [tokenizer](https://github.com/apple-aiml-research/ml-mobileclip/blob/48faa0fea4b08d74188b3841771aca6ff2c92852/ios_app/MobileCLIPExplore/Tokenizer/CLIPTokenizer.swift).

Code is MIT with separately acknowledged Apache-2.0 tokenizer material. **Current repository `LICENSE_MODELS` limits weights/derivatives to noncommercial scientific research and explicitly excludes product development/commercial services.** Model weights cannot be treated as MIT merely because the code is MIT. [Code licence](https://github.com/apple-aiml-research/ml-mobileclip/blob/48faa0fea4b08d74188b3841771aca6ff2c92852/LICENSE), [model licence](https://github.com/apple-aiml-research/ml-mobileclip/blob/48faa0fea4b08d74188b3841771aca6ff2c92852/LICENSE_MODELS), [tokenizer acknowledgements](https://github.com/apple-aiml-research/ml-mobileclip/blob/48faa0fea4b08d74188b3841771aca6ff2c92852/ios_app/ACKNOWLEDGEMENTS).

There is also a separately published `apple/coreml-mobileclip` artifact, revision `3e0a7bfb9fe83da8a3efaa3fd8f7df24214bb947`. Its card labels `apple-ascl` and links a historical `LICENSE_weights_data` path; that path is absent from current upstream. No licence file was listed in that model revision. Therefore the exact grant governing those already converted artifacts needs resolution before product selection. Do not collapse this older artifact's licence metadata into the newer research-only repository licence, or assume an obsolete link clears commercial redistribution. `apple/MobileCLIP-S0` revision `71aa3e13dda93115871afbd017336535ba29886c` separately labels `apple-amlr`. [Core ML artifact card](https://huggingface.co/apple/coreml-mobileclip/blob/3e0a7bfb9fe83da8a3efaa3fd8f7df24214bb947/README.md), [S0 card and licence](https://huggingface.co/apple/MobileCLIP-S0/tree/71aa3e13dda93115871afbd017336535ba29886c).

### CLIP and SigLIP: model/conversion comparisons

OpenAI CLIP source at `d05afc436d78f1c48dc0dbf8e5980a9d471f35f6` (25 March 2026) provides MIT Python code and matched `encode_image`/`encode_text` APIs, with BPE tokenization and model transforms. The model card stresses English and task-specific validation. This is a source for a converted comparison baseline; it does not itself provide a first-party Swift package or establish a ready Core ML artifact for this app. Conversion, exact checkpoint provenance/terms, tokenizer parity, preprocessing and numerical validation remain integration work. [Source and API](https://github.com/openai/CLIP/blob/d05afc436d78f1c48dc0dbf8e5980a9d471f35f6/README.md), [licence](https://github.com/openai/CLIP/blob/d05afc436d78f1c48dc0dbf8e5980a9d471f35f6/LICENSE), [model card](https://github.com/openai/CLIP/blob/d05afc436d78f1c48dc0dbf8e5980a9d471f35f6/model-card.md).

Google-published `siglip-base-patch16-224`, revision `7fd15f0689c79d79e38b1c2e2e2370a7bf2761ed`, is labelled Apache-2.0 and supports image/text retrieval. Its checkpoint is a heavier comparison candidate; the model card describes 224px images and 64-token text. Its Python/Transformers interface does not make the CLIP BPE tokenizer interchangeable. A native implementation must match this checkpoint's tokenizer, padding, normalization and projection. No first-party Swift/Core ML package was established in this pass, so it ranks behind UForm for immediate reuse. [Model card](https://huggingface.co/google/siglip-base-patch16-224/blob/7fd15f0689c79d79e38b1c2e2e2370a7bf2761ed/README.md), [publisher implementation](https://github.com/google-research/big_vision/tree/main/big_vision/configs/proj/image_text).

## Existing app code to reuse selectively

`mazzzystar/Queryable` at `b95a05a8ac1bee2d703af869b9e9e996dd9672bd` (29 March 2026) is MIT Swift app code for offline text-to-photo retrieval. It precomputes image embeddings and encodes each query once. Concrete modules include `Queryable/Queryable/CLIP/ImgEncoder.swift`, `CLIP/TextEncoder.swift`, `Model/EmbeddingStore.swift`, `Model/GPUSimilaritySearch.swift` and `ViewModel/PhotoSearcher.swift`. [Repository README](https://github.com/mazzzystar/Queryable/blob/b95a05a8ac1bee2d703af869b9e9e996dd9672bd/README.md), [licence](https://github.com/mazzzystar/Queryable/blob/b95a05a8ac1bee2d703af869b9e9e996dd9672bd/LICENSE).

`ImgEncoder.swift` includes pixel-buffer reuse and explicit detachment of inference output from IOSurface storage. `EmbeddingStore.swift` uses append-only additions/tombstones around a fixed 512-float record format. These are useful extraction/reference points, but the store assumes its app's single-writer context and uses ordinary file writes. Our shared keyboard/companion access, encrypted persistence, 256-dimensional candidate model, source revisions and Forget semantics require adaptation. Default models are MobileCLIP-S2 with separately downloaded weights, so the app's MIT code licence does not resolve weight licensing. [Image pipeline](https://github.com/mazzzystar/Queryable/blob/b95a05a8ac1bee2d703af869b9e9e996dd9672bd/Queryable/Queryable/CLIP/ImgEncoder.swift), [store](https://github.com/mazzzystar/Queryable/blob/b95a05a8ac1bee2d703af869b9e9e996dd9672bd/Queryable/Queryable/Model/EmbeddingStore.swift), [text encoder](https://github.com/mazzzystar/Queryable/blob/b95a05a8ac1bee2d703af869b9e9e996dd9672bd/Queryable/Queryable/CLIP/TextEncoder.swift).

USearch's Swift/C API can supply nearest-neighbour lookup after encoding; it does not supply a multimodal encoder. Existing [search-engine reuse research](2026-10-22-reuse-search-engines.md) covers its interface/licence and sqlite-vec. A bounded exact-vector baseline can be sufficient to assess model relevance before adding graph-index complexity.

## Image preparation and execution placement

**Proposed engineering boundary:** provision/compile assets and batch-process saved images in the companion/Mac app, then persist per-asset OCR and embeddings. Keyboard Find reads those precomputed representations and only encodes the current query if that encoder passes actual extension measurements. This reduces repeated image work and avoids loading both encoders merely to open Find. It is a recommendation, not a claimed platform requirement or approved feature omission.

Image orientation, colour conversion, downsampling and model-specific normalization must be consistent with the selected checkpoint. Preserve the original asset. Model square-cropping is input preparation, not automatically a user-visible crop feature. UForm's current helper centre-crops; this can discard content near screenshot/document edges. OCR should examine the relevant original/document area independently, and a multi-crop/tile strategy should only be selected if evaluation demonstrates the need. Document quadrilaterals can reuse Vision's `VNDetectDocumentSegmentationRequest`; handwritten cropping algorithms are unnecessary for that selected job. [UForm preparation](https://github.com/unum-cloud/uform/blob/f4beec53743b44ffaad4ff754d65f6c2d347bbd9/swift/Encoders.swift), [Apple document segmentation](https://developer.apple.com/documentation/vision/vndetectdocumentsegmentationrequest).

Apple allows framework use in extensions but documents lower memory budgets and the need to avoid blocking UI. No source here establishes a universal numeric keyboard memory ceiling. OCR or a small image transform is not inherently companion-only; heavy batch encoding belongs there by design. A companion cannot be assumed to stay alive as an inference server while another app's keyboard is visible. If the query model fails extension budgets, the product must explicitly choose its available experience instead of silently advertising semantic image Find. [Extension efficiency](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionCreation.html), [keyboard constraints](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/CustomKeyboard.html).

A 256-dimensional Float32 embedding is 1,024 bytes: 10,000 single-image vectors occupy about 10.24 MB before index structures, IDs, metadata, OCR, thumbnails and models. Multiple crops multiply that cost. This arithmetic is not a measured resident set. Evaluate cold load, query encoding, retrieval, peak memory/energy and termination on supported real phones; simulator and publisher ANE timings are insufficient.

## Gates before a product promise

- Keep searchable attachment text distinct from visual semantic retrieval in implementation/status evidence.
- Validate chosen model/weights/converted artifact/tokenizer licences at pinned revisions; retain notices.
- Compare on captured examples: receipts/screenshots, photos without captions, mixed layouts, small important edge content, no-answer queries, ambiguous scenes and language cases actually selected for support.
- Record model/preprocessing revision and original asset hash; invalidate OCR/vectors when source changes. Reject delayed work for deleted originals.
- Protect OCR, vectors, thumbnails, crop coordinates and caches as vault-derived personal data. The libraries evaluated here do not by themselves supply encryption or a complete Forget boundary.
- Preserve immediate capture and lexical Find while derived work is pending; no batch image encoder should block saving a note.

Root owns the resulting MVP definition and acceptance choice. This note supplies reusable components and limitations without claiming all image modes are implemented or approved.
