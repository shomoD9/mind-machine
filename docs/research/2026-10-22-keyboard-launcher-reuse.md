# Keyboard and Mac launcher reuse

Researched 22 October 2026. This report recommends an integration pilot; no dependency was added and no existing keyboard behavior was replaced.

Keep the working keyboard workspace and native Mac application. Evaluate **SnipKey's MIT keyboard engine** behind our existing typing interface. Build the compact Mac search panel with AppKit and the shared local search service. RustCast is retired; adopting its whole application would add a second application architecture without supplying our vault, semantic retrieval, or iPhone client.

## SnipKey pilot boundary

The source has a useful separation: `NativeKeyboardV2View` owns the key plane, while `KeyboardActions` carries insertion, deletion, caret movement, and other callbacks. UIKit/CALayer handles keys; the toolbar is separate. The action type also references SnipKey snippets, reminders, clipboard operations, and application settings, so it needs an adapter and selective extraction. It is not a drop-in package. [Key-plane source](https://github.com/jtvargas/SnipKey/blob/7797d3992da53369ee034ba1e483bdc4db859c4d/SnipKeyboard/QWERTY/V2/NativeKeyboardV2View.swift), [actions](https://github.com/jtvargas/SnipKey/blob/7797d3992da53369ee034ba1e483bdc4db859c4d/SnipKeyboard/QWERTY/KeyboardActions.swift), [commit pipeline](https://github.com/jtvargas/SnipKey/blob/7797d3992da53369ee034ba1e483bdc4db859c4d/SnipKeyboard/QWERTY/V2/KeyboardCommitPipeline.swift).

Preserve our capture/find/chat workspace, rich-text editor, size modes, saved drafts, host/private-note routing, reminders, and vault ownership. Try only the typing engine in an isolated prototype. Compare rapid typing, rollover touches, delete repeat, punctuation, caret movement, switching destinations, extension memory, and cold activation on a real iPhone. Adopt it only if those checks improve the current experience. Its documentation includes uninstrumented timing claims and stale descriptions; report measured results from our devices. [Upstream architecture and its stated limitations](https://github.com/jtvargas/SnipKey/blob/7797d3992da53369ee034ba1e483bdc4db859c4d/V2_KEYBOARD_ARCHITECTURE.md).

Exclude upstream CloudKit/SwiftData storage, purchases, usage tracking, and debug recording from the extraction. The inspected `TypingTelemetry` can write row/column touch events to the shared container when enabled; its master switch defaults to false. Treat key-position sequences as sensitive even when character strings are absent. We do not need that recording. [Telemetry source](https://github.com/jtvargas/SnipKey/blob/7797d3992da53369ee034ba1e483bdc4db859c4d/SnipKeyboard/QWERTY/V2/TypingTelemetry.swift), [storage provider](https://github.com/jtvargas/SnipKey/blob/7797d3992da53369ee034ba1e483bdc4db859c4d/SnipKeyboard/QWERTY/V2/ModelContainerProvider.swift).

If MIT code is copied, retain its copyright and permission notice with all copies or substantial portions. Keep upstream provenance and a pinned revision in third-party notices. Assets and data need separate inspection: SnipKey's Unicode emoji data has its own notice, which must accompany that data if adopted. Do not copy the app's branding, tip-jar configuration, or unrelated dependencies. [MIT terms](https://github.com/jtvargas/SnipKey/blob/7797d3992da53369ee034ba1e483bdc4db859c4d/LICENSE), [Unicode data notice](https://github.com/jtvargas/SnipKey/blob/7797d3992da53369ee034ba1e483bdc4db859c4d/SnipKeyboard/Resources/emoji-unicode-license.txt).

## Mac panel near the text field

Apple's public accessibility interfaces expose the focused UI element, selected text range, and bounds for a range. Reading the **range and geometry** can locate a caret without reading the field's text. Calls can fail when an application omits or cannot supply an attribute. Accessibility trust is required for cross-application access. Permission covers broader abilities than geometry; the app should explain and restrict its own use. [Focused element](https://developer.apple.com/documentation/applicationservices/kaxfocuseduielementattribute), [selected range](https://developer.apple.com/documentation/applicationservices/kaxselectedtextrangeattribute), [range bounds](https://developer.apple.com/documentation/applicationservices/kaxboundsforrangeparameterizedattribute), [parameterized calls and errors](https://developer.apple.com/documentation/applicationservices/1461203-axuielementcopyparameterizedattr), [trust check](https://developer.apple.com/documentation/applicationservices/1459186-axisprocesstrustedwithoptions).

Proposed behavior, pending native validation:

1. On the explicit hotkey, sample the previously focused app before activating our panel. Request only element identity, range, position, and size; never the field value, selected string, document text, or browsing context.
2. Prefer the caret/selection rectangle, then the focused text field's rectangle. Place the small panel beside or below it and constrain it to the available screen. Keep the typed query inside our panel.
3. If permission is declined, geometry is missing, the field is secure, or the app fails to respond promptly, open the same compact panel in a predictable position on the active screen. Search remains usable without Accessibility permission.
4. Query the local index as the user types; cancel obsolete queries and discard stale results. Any semantic enrichment must leave typing and first lexical results responsive. This is an architectural requirement, rather than a measured result from these launcher projects.

The local Xcode macOS SDK headers independently confirm `AXIsProcessTrustedWithOptions`, `kAXSelectedTextRangeAttribute`, `kAXFocusedUIElementAttribute`, `kAXBoundsForRangeParameterizedAttribute`, and the cross-process error cases. No arbitrary app can be promised to expose an accurate caret rectangle. This feature needs tests in ordinary native fields, Chrome editable fields, Electron apps, secure fields, multiple monitors, and permission-denied mode.

## iPhone boundary

An iOS custom keyboard replaces the system keyboard. Apple's public extension API gives us our own input view; it does not offer an embeddable Apple keyboard to place beneath our notepad. Apple's guide also says custom keyboards draw within their own primary view, secure fields use the system keyboard, and host applications can reject custom keyboards. Reusing another engine cannot remove these platform boundaries. [Apple custom keyboard guide](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/CustomKeyboard.html).

The app and extension can share an App Group, but access needs coordination. Our local retrieval service should sit behind a common interface used by the keyboard and Mac panel, regardless of the chosen typing engine. Keep account, sync, and AI setup in consumer-facing app settings; the key plane should not require technical server configuration. [Apple shared-container guidance](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionScenarios.html).

## Decision proposed

Use the current Swift native client as the baseline. Authorize a small SnipKey key-plane pilot before adopting any code. Keep search, storage, encrypted sync, and AI providers as separate modules with measured contracts. A native AppKit search panel already fits the requested Mac shape; Rust becomes justified only by a measured backend bottleneck or a concrete cross-platform reuse benefit. RustCast supplies neither evidence by itself.
